# Shop 生产发布检查清单

**适用范围：** 包含 Flyway `V85` 至 `V90` 的商家自营电商版本
**最后更新：** 2026-08-09

本清单是发布门禁，不是“示例配置”。每一项只有在真实环境执行并保存证据后才能
勾选。仓库目前没有已确认的生产 API/后台域名、商家主体证照、正式法律文本或商品
标签事实；这些项目未补齐前，结论只能是“禁止发布”，不能用开发域名、测试证照、
占位协议或虚构食品信息代替。

自动化测试只能证明代码路径。它不能证明真实微信登录/支付/发货/退款、官方物流
插件、电子面单打印、COS、WebSocket、地图地址、微信审核上传或真机行为。

## 1. 发布负责人和证据

- [ ] 记录待发布 Git 提交、构建产物摘要、构建时间和批准人；禁止从未记录的本地脏
      工作区直接构建生产包。
- [ ] 指定发布负责人、数据库负责人、商家合规负责人、微信平台负责人、客服/售后
      负责人和回滚决策人。
- [ ] 明确维护窗口、停止写入时间、预计恢复时间、回滚判断时点和通知渠道。
- [ ] 建立一次发布证据目录，保存自动化输出、只读 SQL 导出、迁移日志、配置校验、
      匿名接口响应、真机截图/录屏和异常处置记录；不得保存密钥、完整 OpenID、手机号、
      地址、支付凭据或未脱敏证照。
- [ ] 确认本次发布保留个人中心 V 头像框、皇冠、`金牌会员` 文案、会员卡素材和登录
      展示条件；合规与账户权利入口位于会员卡之外，不删除或重做该展示。

## 2. 自动化和代码门禁

从仓库根目录执行，并保存完整退出码与摘要：

```bash
cd backend/shop-server
./mvnw test

cd ../../admin
pnpm check
pnpm build

cd ../miniprogram
pnpm check

cd ..
git diff --check
git status --short --branch
```

- [ ] 后端完整测试零失败、零错误。Docker 不可用造成的 Testcontainers 错误必须按
      精确测试名记录，不能写成通过。
- [ ] 在可用 Docker 环境用一次性 MySQL 执行迁移和并发敏感测试；H2 通过不能替代
      MySQL 的锁、索引、唯一约束与 Flyway 兼容性验证。
- [ ] Admin `check`、生产构建以及 Mini Program `check` 全部通过。
- [ ] 人工审查发布差异：只包含批准范围，没有 `.env.*.local`、PEM、密钥、生产 URL、
      证照原图、数据库导出、用户数据或构建临时文件。
- [ ] Mini Program 源码契约和真机均确认 `金牌会员` 展示不变量没有变化。

聚焦命令见 [dev-setup.md](dev-setup.md#v85-v90-focused-gates)，安全本地接口步骤见
[smoke-checks.md](smoke-checks.md#compliance-and-account-rights-smoke-checks)。

## 3. MySQL 备份、迁移演练和回滚

### 3.1 迁移前

- [ ] 使用与生产相同 MySQL 大版本和字符集，将最新生产备份恢复到隔离数据库；严禁
      对生产库或开发者持久库执行 `Flyway clean`。
- [ ] 在隔离库启动候选版本，让 Flyway 从当前版本依次执行到 `V90`，保存迁移耗时、
      警告和 `flyway_schema_history`。
- [ ] 演练库通过 V85/V86 对账、V87 发货状态报告、V89 在售分类报告和发布后不变量。
- [ ] 确认 `V85` 至 `V90` 文件未修改任何已在目标环境执行过的旧迁移校验和。
- [ ] 评估 V89 的维护窗口工作量：历史在售商品会成为 `UNCLASSIFIED`，但迁移不会
      自动下架；恢复流量前必须逐一处理。

在生产维护窗口开始且业务写入停止后，执行已有备份脚本：

```bash
sudo /opt/shop/shop-server/scripts/backup-mysql.sh
```

- [ ] 记录备份文件名、时间、大小和校验摘要；在隔离 MySQL 实际恢复并抽查核心表，
      不能只确认文件存在。
- [ ] 备份另存到不同故障域；仅留在同一主机不能防止磁盘或整机故障。日常备份流程见
      [docker-deployment.md](docker-deployment.md#自动备份)。
- [ ] 记录停写后的订单、支付、退款、发货和售后行数/最大 ID，作为恢复一致性基线。

### 3.2 迁移后

确认六个迁移都成功：

```sql
select installed_rank, version, description, installed_on, success
from flyway_schema_history
where version in ('85', '86', '87', '88', '89', '90')
order by installed_rank;
```

- [ ] 六行均存在且 `success = 1`，应用健康检查通过，没有重复索引、约束或权限种子错误。
- [ ] 继续保持公网业务入口关闭，先完成本清单中的历史数据、真实发布数据和外部联调。

### 3.3 回滚决策

- [ ] 发布前确认旧应用是否经过验证可以读取 `V90` 结构；未经验证不得只切旧镜像。
- [ ] 不编写临时反向 SQL 删除 V85-V90 列、表或数据，也不执行 `Flyway clean`。
- [ ] 若候选应用失败但数据库结构向后兼容，优先保留数据库并回到已验证兼容镜像，或
      向前修复。
- [ ] 若必须恢复迁移前数据库，继续阻断所有写入，恢复已验证备份，并同步恢复匹配的
      应用版本。备份时点之后的交易会丢失，必须由回滚决策人确认并完成支付/退款/微信
      渠道对账后才能重新开放。
- [ ] 应用镜像回切方法见 [docker-deployment.md](docker-deployment.md#检查与回滚)；数据库
      能否恢复是独立决策，不能把“容器已启动”当作数据已回滚。

## 4. 真实域名、网关和微信平台

当前仓库只知道开发 API 地址；正式版 API 值故意为空并 fail closed。

- [ ] 商家书面确认真实生产 API 域名、后台域名、支付/退款回调根域名和必要的静态/COS
      域名；DNS、有效 HTTPS 证书、续期、HSTS/代理策略和网关路由均已验证。
- [ ] `miniprogram/miniprogram/config/app-config.ts` 的 release 配置使用确认后的生产 HTTPS
      API；不得使用空值、localhost、loopback、包含 `pay-dev` 的开发主机或临时隧道。
- [ ] `trial` 当前明确复用开发 API 且仅隔离会话命名空间；它不是独立预发布环境，不能
      用体验版连接开发后端的结果替代生产验收。
- [ ] 微信公众平台配置与实际请求完全一致：`request` 业务 API，`uploadFile` COS 客户端
      域名，`downloadFile` COS/历史兼容源站及实际使用的微信头像域名。
- [ ] 反向代理只信任明确 CIDR，替换而非盲目信任外部 `X-Forwarded-For`；MySQL/Redis
      只暴露在回环或内部网络。
- [ ] 微信支付 AppID、商户号、证书/公钥、APIv3、回调和运行来源配置均来自受控生产
      存储；不把值写入仓库、日志、截图或发布证据。
- [ ] 回调公网路径能够到达当前应用，支付和退款签名/解密成功；若启用按单路由，所有
      实例先支持 `/r/{opaque-token}`，旧固定回调在渠道重试窗口内继续受限保留。
- [ ] 微信小程序后台的隐私保护指引、服务类目、支付、客服、物流助手/发货信息管理、
      物流插件和所需消息能力与本次实际功能一致。
- [ ] COS 桶、区域、数据万象、CAM 最小权限、CORS、生命周期、公开/私有访问和微信
      合法域名按 [cos-direct-upload.md](cos-direct-upload.md) 实测通过。

## 5. 商家主体、证照和法律文本（V88）

V88 不创建任何公共默认值。以下内容必须由商家和相应审核人提供：

- [ ] 真实法定主体名称、主体类型、统一社会信用代码、经营地址。
- [ ] 对外客服和投诉联系方式，已验证有人接听/处理且展示范围得到批准。
- [ ] 当前有效营业执照原图已通过受管素材上传，并核对主体、号码与有效状态。
- [ ] 适用的真实食品经营许可/备案类型、号码、有效期和原图已核对；不适用时先由商家
      合规负责人决定产品和系统范围，不能随意填写一张假证照通过校验。
- [ ] 隐私政策、用户协议、售后服务政策已由负责人审核，包含实际主体、联系方式、
      数据处理、支付/履约/售后规则和生效时间，没有“待填写”“示例”“占位”等内容。
- [ ] 三份文档使用明确版本号创建草稿，预览无误后发布；已发布修订不原地修改，新版
      发布后保留不可变历史。
- [ ] 匿名接口只返回当前发布版本，内容和证照 URL 与后台批准版本一致：

```text
GET /app/compliance/merchant
GET /app/compliance/documents/PRIVACY_POLICY/current
GET /app/compliance/documents/USER_AGREEMENT/current
GET /app/compliance/documents/AFTER_SALE_POLICY/current
```

- [ ] 生产环境强制隐私同意；未勾选、过期版本或非当前版本登录均失败，正确版本在用户
      主动点击后才调用 `wx.login`，并原子记录版本、摘要、环境和服务端时间。
- [ ] 在尚未发布当前隐私政策时保持业务入口关闭，因为生产登录会按设计失败。

## 6. 商品分类和食品披露（V89）

迁移后先执行：

```sql
select id, title, status, compliance_type
from product_spu
where deleted_at is null
  and status = 'ON_SALE'
  and compliance_type = 'UNCLASSIFIED'
order by id;
```

- [ ] 导出并由商品负责人逐行确认；开放流量前结果必须为零。
- [ ] `ON_SALE + UNCLASSIFIED` 不能直接补资料时，先下架，再保存真实分类/披露，审核后
      才重新发布。迁移不会自动伪造分类，也不会自动下架旧商品。
- [ ] 只有确实不是食品的商品才选 `NON_FOOD`；不得复制 smoke 中的锅垫分类到真实食品。
- [ ] 每个 `FOOD` SPU 使用实际包装核对食品名称、配料、贮存条件、保质期说明、生产者、
      地址、生产许可证号、产地及实际适用的过敏原/消费提示。
- [ ] 每个启用 SKU 都填写与实物一致的净含量文本。
- [ ] 至少上传一张清晰、完整、当前批次适用的原始包装/标签图片；文件属于受管素材，
      展示 URL 与文件 ID 一致，删除保护生效。
- [ ] 批次/生产日期随实物变化时只使用经审核且真实的“以包装标示为准”等表述，不填写
      虚构固定日期；可选字段没有事实就保持空白，不编造“无”。
- [ ] 发布 FOOD 前存在当前有效、已发布的商家食品资质；资质过期或缺失时发布必须失败。
- [ ] 小程序食品信息卡在自由图文详情之前展示，字段、SKU 净含量和标签预览与实物一致；
      `NON_FOOD/UNCLASSIFIED` 不显示成食品披露。

## 7. 订单期限与退款库存对账（V85/V86）

完整 SQL 和解释以 [transaction-reconciliation.md](transaction-reconciliation.md) 为准。

- [ ] 使用只读账号执行 V85 迁移前 `CREATED` 分类报告，分别核对有/无支付记录的订单。
- [ ] 导出商品项、库存锁、优惠券和支付证据；任何映射缺失或状态矛盾的订单先隔离人工
      处理。
- [ ] 不对历史 `payment_expires_at IS NULL` 做无界批量回填，不让新 worker 盲目关闭历史
      订单；若商家批准一次性回填，单独评审固定 ID 清单和前后计数。
- [ ] 新订单固定保存同一个支付截止时间，支付发起不得延长；发布后两个 V85 不变量查询
      均返回空集。
- [ ] 使用只读账号导出历史成功退款候选，逐单核对微信退款、仓库/发货、库存锁和既往
      人工调账。
- [ ] V86 不自动补历史库存；禁止手工伪造 `REFUND_RESTOCK` 日志或直接把历史锁改为
      `RESTOCKED`。
- [ ] 新的已支付未发货全额退款在渠道确认成功后只回补一次；已发货/已完成退款不增加
      可售库存，重复回调不增加库存或日志。
- [ ] 发布后 V86 不变量查询为空；若有异常，停用受影响操作，保存具体订单/退款证据并
      逐单处理，不做无界修复 SQL。

## 8. 微信发货可靠投递和收货（V87）

首次迁移/切流建议先关闭外部发送和收货扫描：

```properties
SHOP_WECHAT_SHIPPING_UPLOAD_ENABLED=false
SHOP_WECHAT_SHIPPING_DELIVERY_ENABLED=false
SHOP_WECHAT_RECEIPT_RECONCILIATION_ENABLED=false
```

- [ ] 迁移前导出 `order_shipment` 按 `wechat_provider_mode + wechat_upload_status` 的数量和
      具体非终态 ID。V87 会把遗留 `UPLOADING` 标为 `UNKNOWN`，并可能把真实/未知提供方
      下的已发货 `SKIPPED` 转为 `PENDING`；这些是待对账工作，不是已上传证明。
- [ ] 迁移后检查所有待处理状态：

```sql
select wechat_provider_mode, wechat_upload_status, count(*) as shipment_count
from order_shipment
group by wechat_provider_mode, wechat_upload_status
order by wechat_provider_mode, wechat_upload_status;

select id, order_id, wechat_provider_mode, wechat_upload_status,
       wechat_upload_attempt_count, wechat_upload_not_uploaded_observations,
       wechat_upload_claimed_at, wechat_upload_next_action_at,
       wechat_error_code, updated_at
from order_shipment
where wechat_upload_status in
      ('PENDING', 'UPLOADING', 'FAILED', 'UNAVAILABLE', 'UNKNOWN')
order by id;
```

- [ ] 对每个 `UNKNOWN` 使用微信 `get_order` 和本地订单/物流事实核对；身份或物流信息不
      一致时保持未知，禁止盲目重复上传。
- [ ] `FAILED` 由运营根据安全错误码决定修复/重试；`UNAVAILABLE/PENDING` 只在真实凭据、
      订单和监控准备后进入有界调度。
- [ ] 使用真实低风险已支付订单验证 AppID、payer OpenID、微信支付交易号、商品/物流
      数据匹配，再逐步启用 upload、delivery 和 receipt reconciliation。
- [ ] `REAL + UPLOADED` 由微信收货状态主导；`UPLOADING/UNKNOWN` 阻止本地收货；明确未
      上传或非真实提供方的路径只写入审计化本地确认，不声称微信已确认。
- [ ] 真实上传出现网络不确定时，验证 claim token、退避、过期接管和终态 fencing；多
      实例不能重复创建发货事实。
- [ ] 电子面单沙箱只证明微信 TEST 能力，不代表生产承运商绑定、真实轨迹或物理打印。
      正式验收使用真实订单、承运商、运单、收件人、付款人和设备。

## 9. 账户权利人工处理（V90）

- [ ] 为账户注销、个人信息删除、访问/复制、更正分别指定负责人、处理 SLA、身份核验、
      升级路径、拒绝条件和通知模板。
- [ ] 与商家/法律负责人确认真实保留规则：哪些交易、支付、退款、售后和审计数据必须
      保留、依据、期限、访问范围和到期删除方式。系统不替商家作这个决定。
- [ ] 管理员每次 review/approve/reject/complete 使用当前版本，并填写针对该申请的真实
      原因与保留说明；`retainedDataCategories=[]` 只表示经核对确实没有保留类别，不能
      为省事留空。
- [ ] `ACCESS_COPY` 和 `CORRECTION` 当前是受理/审计工作流；运营必须实际完成数据导出或
      更正并保存交付证据后才能标记完成，状态按钮本身不会自动生成副本或修改所有业务表。
- [ ] 注销使用同一账号新取得的一次性微信 code；旧 code、其他用户 code 或客户端自报
      OpenID 均不能作为身份依据。
- [ ] 注销/个人信息删除完成前核对活动订单、支付、退款和售后；存在未结业务时保持阻断，
      不人工绕过。
- [ ] 使用专用、可丢弃的真实测试账号验证完成后旧 access/refresh token 均失效，用户
      不能继续访问；不得在商家、员工或真实顾客账号上试验注销。
- [ ] 核对最小化结果和必须保留的交易/审计记录，确认后台审计链包含操作者、状态、原因、
      保留说明、类别和时间。

## 10. 基础设施和运维

- [ ] 生产 profile 从受控 `.env.prod.local` 读取，文件权限、密钥挂载和 Redis/MySQL
      密码符合 [docker-deployment.md](docker-deployment.md)；本地测试账号和已知密码未启用。
- [ ] Redis 可用；管理员登录保护、会话撤销和 app token auth-version 检查在故障模式下
      fail closed。
- [ ] 支付/退款/发货 HTTP 连接、读取和响应体大小都有边界；日志只保留安全错误摘要。
- [ ] 定时任务只有在对应历史对账完成后启用，批量、租约、退避和告警阈值已配置。
- [ ] 监控覆盖应用健康、HTTP 5xx/401/429、登录失败、支付/退款回调、超时关闭、退款
      恢复、发货 PENDING/UNKNOWN/FAILED、收货对账、账户权利积压、数据库/Redis/COS。
- [ ] 客服/投诉值班、订单/库存/退款人工对账和账号权利工单有实际人员接手。

## 11. 微信开发者工具与真机 smoke

使用专用测试数据和可控低金额真实订单；每项记录环境、账号角色、订单号脱敏摘要、时间和
结果。模拟器通过不能替代真机。

- [ ] 正式配置包启动并只请求生产 API；开发/体验/正式会话不串用。
