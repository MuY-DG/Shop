# Shop 生产发布检查清单

**适用范围：** 包含 Flyway `V85` 至 `V105` 的商家自营电商版本
**最后更新：** 2026-08-21

本清单是发布门禁，不是“示例配置”。每一项只有在真实环境执行并保存证据后才能
勾选。正式 API `api.muybaby6.icu` 与后台 `admin.muybaby6.icu` 已建立 DNS 和 SAN TLS
基线，但仓库仍没有可以自动确认的商家主体证照、正式法律文本或商品标签事实。
这些项目和真实微信验收未补齐前，不能用测试证照、占位协议或虚构食品信息代替。

自动化测试只能证明代码路径。它不能证明真实微信登录/支付/发货/退款、官方物流
插件、电子面单打印、COS、WebSocket、地图地址、微信审核上传或真机行为。

V93 的准确范围是下载微信交易账单 `ALL`，按中国业务日与本地成功支付/退款记录
核对，并提供差异处理、原始账单受控下载和 CSV 导出。它不下载微信资金账单，不核对
微信商户账户余额或银行到账，也不应被描述为银行对账。V93 不包含“支付成功、发货、
退款成功、客服回复、低库存”等订阅消息能力。

V94 只新增微信新版 `notify_type=2001` “购物（实体物流）服务动态”。它不是
`wx.requestSubscribeMessage` 传统订阅消息，也不等于已具备客服回复或低库存通知。
意图采集、set/get 外呼 Worker 和 SAFE+JSON 结果回调的部署默认值全部关闭。当前生产
已单独启用 Callback 并完成 GET 握手，Capture/Worker 仍关闭；代码或自动化通过不得
表述为微信卡片已生产送达。

## 3. MySQL 备份、迁移演练和回滚

### 3.1 迁移前

- [ ] 使用与生产相同 MySQL 大版本和字符集，将最新生产备份恢复到隔离数据库；严禁
      对生产库或开发者持久库执行 `Flyway clean`。
- [ ] 在隔离库启动候选版本，让 Flyway 从当前版本依次执行到 `V102`，保存迁移耗时、
      警告和 `flyway_schema_history`。
- [ ] 演练库通过 V85/V86 对账、V87 发货状态报告、V89 在售分类报告、V91 管理员注册
      默认关闭、V92 售后 V2 数据不变量、V93 财务表/RBAC/订单清理保护、V94 服务
      动态外键/唯一性/检查约束和订单清理档案、V95/V97/V100 运行开关/CAS 审计/RBAC
      菜单不变量、V98/V99/V101 加密配置，以及 V102 支付软删除约束和权限种子。
- [ ] 确认 `V85` 至 `V101` 文件未修改任何已在目标环境执行过的旧迁移校验和，新增
      `V102` 只以前向迁移方式执行。
- [ ] 评估 V89 的维护窗口工作量：历史在售商品会成为 `UNCLASSIFIED`，但迁移不会
      自动下架；恢复流量前必须逐一处理。

在生产维护窗口开始且业务写入停止后，执行已有备份脚本：

```bash
sudo /opt/shop/shop-server/scripts/backup-mysql.sh
```

- [ ] 记录备份文件名、时间、大小和校验摘要；在隔离 MySQL 实际恢复并抽查核心表，
      不能只确认文件存在。
- [ ] 备份另存到不同故障域；仅留在同一主机不能防止磁盘或整机故障。日常备份流程见
      [docker-deployment.md](docker-deployment.md#自动备份)。
- [ ] 记录停写后的订单、支付、退款、发货和售后行数/最大 ID，作为恢复一致性基线。

### 3.2 迁移后

确认从 V85 到 V102 的十八个迁移都成功：

```sql
select installed_rank, version, description, installed_on, success
from flyway_schema_history
where version in ('85', '86', '87', '88', '89', '90', '91', '92', '93', '94', '95')
   or version in ('96', '97', '98', '99', '100', '101', '102')
order by installed_rank;
```

- [ ] 十八行均存在且 `success = 1`，应用健康检查通过，没有重复索引、约束或权限种子错误。
- [ ] V102 后 `payment_config.deleted_at/deleted_by`、`chk_payment_config_delete_state`、
      `payment:config:delete` 及菜单 802 绑定均存在；删除权限默认只授予 `R_SUPER`，没有
      意外扩散到其他角色。
- [ ] 继续保持公网业务入口关闭，先完成本清单中的历史数据、真实发布数据和外部联调。

### 3.3 回滚决策

- [ ] 发布前确认旧应用是否经过验证可以读取 `V102` 结构；未经验证不得只切旧镜像。
- [ ] 不编写临时反向 SQL 删除 V85-V102 列、表或数据，也不执行 `Flyway clean`。
- [ ] 若候选应用失败但数据库结构向后兼容，优先保留数据库并回到已验证兼容镜像，或
      向前修复。
- [ ] 若必须恢复迁移前数据库，继续阻断所有写入，恢复已验证备份，并同步恢复匹配的
      应用版本。备份时点之后的交易会丢失，必须由回滚决策人确认并完成支付/退款/微信
      渠道对账后才能重新开放。
- [ ] 应用镜像回切方法见 [docker-deployment.md](docker-deployment.md#检查与回滚)；数据库
      能否恢复是独立决策，不能把“容器已启动”当作数据已回滚。

## 5. 商家主体、证照和法律文本（V88）

V88 不创建任何公共默认值。以下内容必须由商家和相应审核人提供：

- [ ] 真实法定主体名称、主体类型、统一社会信用代码、经营地址。
- [ ] 对外客服和投诉联系方式，已验证有人接听/处理且展示范围得到批准。
- [ ] 当前有效营业执照原图已通过受管素材上传，并核对主体、号码与有效状态。
- [ ] 适用的真实食品经营许可/备案类型、号码、有效期和原图已核对；不适用时先由商家
      合规负责人决定产品和系统范围，不能随意填写一张假证照通过校验。
- [ ] 隐私政策、用户协议、售后服务政策和账号注销须知已由负责人审核，包含实际主体、联系方式、
      数据处理、支付/履约/售后规则和生效时间，没有“待填写”“示例”“占位”等内容。
- [ ] 四份文档使用明确版本号创建草稿，预览无误后发布；已发布修订不原地修改，新版
      发布后保留不可变历史。
- [ ] 匿名接口只返回当前发布版本，内容和证照 URL 与后台批准版本一致：

```text
GET /app/compliance/merchant
GET /app/compliance/documents/PRIVACY_POLICY/current
GET /app/compliance/documents/USER_AGREEMENT/current
GET /app/compliance/documents/AFTER_SALE_POLICY/current
```

- [ ] 微信小程序平台的“用户隐私保护指引”已按实际使用能力配置并审核；登录页显示平台
      返回的指引名称，点击后由 `wx.openPrivacyContract` 只读展示。
- [ ] 未勾选时不调用 `wx.login`；勾选后才开始登录预加载，用户点击“微信一键登录”后
      才提交本地会话。后台自建隐私政策是否发布不阻塞小程序登录。

## 6. 商品分类和食品披露（V89）

迁移后先执行：

```sql
select id, title, status, compliance_type
from product_spu
where deleted_at is null
  and status = 'ON_SALE'
  and compliance_type = 'UNCLASSIFIED'
order by id;
```

- [ ] 导出并由商品负责人逐行确认；开放流量前结果必须为零。
- [ ] `ON_SALE + UNCLASSIFIED` 不能直接补资料时，先下架，再保存真实分类/披露，审核后
      才重新发布。迁移不会自动伪造分类，也不会自动下架旧商品。
- [ ] 只有确实不是食品的商品才选 `NON_FOOD`；不得复制 smoke 中的锅垫分类到真实食品。
- [ ] 每个 `FOOD` SPU 使用实际包装核对食品名称、配料、贮存条件、保质期说明、生产者、
      地址、生产许可证号、产地及实际适用的过敏原/消费提示。
- [ ] 每个启用 SKU 都填写与实物一致的净含量文本。
- [ ] 至少上传一张清晰、完整、当前批次适用的原始包装/标签图片；文件属于受管素材，
      展示 URL 与文件 ID 一致，删除保护生效。
- [ ] 批次/生产日期随实物变化时只使用经审核且真实的“以包装标示为准”等表述，不填写
      虚构固定日期；可选字段没有事实就保持空白，不编造“无”。
- [ ] 发布 FOOD 前存在当前有效、已发布的商家食品资质；资质过期或缺失时发布必须失败。
- [ ] 小程序食品信息卡在自由图文详情之前展示，字段、SKU 净含量和标签预览与实物一致；
      `NON_FOOD/UNCLASSIFIED` 不显示成食品披露。

## 7. 订单期限与退款库存对账（V85/V86）

完整 SQL 和解释以 [transaction-reconciliation.md](transaction-reconciliation.md) 为准。

- [ ] 使用只读账号执行 V85 迁移前 `CREATED` 分类报告，分别核对有/无支付记录的订单。
- [ ] 导出商品项、库存锁、优惠券和支付证据；任何映射缺失或状态矛盾的订单先隔离人工
      处理。
- [ ] 不对历史 `payment_expires_at IS NULL` 做无界批量回填，不让新 worker 盲目关闭历史
      订单；若商家批准一次性回填，单独评审固定 ID 清单和前后计数。
- [ ] 新订单固定保存同一个支付截止时间，支付发起不得延长；发布后两个 V85 不变量查询
      均返回空集。
- [ ] 使用只读账号导出历史成功退款候选，逐单核对微信退款、仓库/发货、库存锁和既往
      人工调账。
- [ ] V86 不自动补历史库存；禁止手工伪造 `REFUND_RESTOCK` 日志或直接把历史锁改为
      `RESTOCKED`。

## 8. 微信发货可靠投递和收货（V87）

首次迁移/切流先通过 `GET/PUT /admin/wechat-shipping/runtime` 将上传、可靠投递和收货
对账三个数据库运行开关全部关闭。写入必须携带当前版本和变更原因，并确认
`wechat_shipping_runtime_audit` 已记录审计。环境变量只允许作为尚无运行时记录时的旧部署
默认值，不再写入新生产模板。

- [ ] 迁移前导出 `order_shipment` 按 `wechat_provider_mode + wechat_upload_status` 的数量和
      具体非终态 ID。V87 会把遗留 `UPLOADING` 标为 `UNKNOWN`，并可能把真实/未知提供方
      下的已发货 `SKIPPED` 转为 `PENDING`；这些是待对账工作，不是已上传证明。
- [ ] 迁移后检查所有待处理状态：

```sql
select wechat_provider_mode, wechat_upload_status, count(*) as shipment_count
from order_shipment
group by wechat_provider_mode, wechat_upload_status
order by wechat_provider_mode, wechat_upload_status;

select id, order_id, wechat_provider_mode, wechat_upload_status,
       wechat_upload_attempt_count, wechat_upload_not_uploaded_observations,
       wechat_upload_claimed_at, wechat_upload_next_action_at,
       wechat_error_code, updated_at
from order_shipment
where wechat_upload_status in
      ('PENDING', 'UPLOADING', 'FAILED', 'UNAVAILABLE', 'UNKNOWN')
order by id;
```

- [ ] 对每个 `UNKNOWN` 使用微信 `get_order` 和本地订单/物流事实核对；身份或物流信息不
      一致时保持未知，禁止盲目重复上传。
- [ ] `FAILED` 由运营根据安全错误码决定修复/重试；`UNAVAILABLE/PENDING` 只在真实凭据、
      订单和监控准备后进入有界调度。
- [ ] 使用真实低风险已支付订单验证 AppID、payer OpenID、微信支付交易号、商品/物流
      数据匹配，再逐步启用 upload、delivery 和 receipt reconciliation。
- [ ] `REAL + UPLOADED` 由微信收货状态主导；`UPLOADING/UNKNOWN` 阻止本地收货；明确未
      上传或非真实提供方的路径只写入审计化本地确认，不声称微信已确认。
- [ ] 真实上传出现网络不确定时，验证 claim token、退避、过期接管和终态 fencing；多
      实例不能重复创建发货事实。
- [ ] 电子面单沙箱只证明微信 TEST 能力，不代表生产承运商绑定、真实轨迹或物理打印。
      正式验收使用真实订单、承运商、运单、收件人、付款人和设备。
