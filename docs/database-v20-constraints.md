# V20 库存与金额约束升级

V20 增加数据库兜底约束，不调整任何历史金额、库存或锁记录。约束覆盖以下业务规则：

- SKU 可售库存、库存预警值、售价、原价和已知成本不能小于零。
- 同一订单商品明细只能存在一条库存锁，包括已经释放的锁；锁定数量和购买数量必须大于零。
- 订单及订单商品明细的价格、金额、折扣和分摊金额不能小于零。
- 库存流水的变更前后数量不能小于零，且必须满足“变更前数量 + 变化量 = 变更后数量”。变化量允许正数、负数和零。

永久删除商品使用的零价 SKU 占位记录仍然有效。成本和历史分摊金额的 `NULL` 继续表示未知，迁移不会将其改成零。跨表数量守恒、金额分摊与订单状态仍由事务内业务逻辑校验。

## 上线前检查

1. 在部署目标库执行 [database-v20-preflight.sql](database-v20-preflight.sql)，保存结果。脚本只执行查询，第一组 `violation_count` 应全部为零；重复库存锁的计数单位是订单项组数，后续查询提供最多 100 个样本。
2. 若存在异常，先对照订单、退款和库存流水确认事实，再制定单独的数据修复。不要直接将负数归零，也不要随意保留一条库存锁并删除其余记录。
3. 按现有备份与发布流程安排迁移窗口。预检到迁移之间若继续有写入，预检结果不能保证最终有效；应协调写入和定时任务，避免旧实例在窗口中产生新数据。增加索引和检查约束会扫描现有表，大表应先在同规模副本评估耗时。
4. 使用正常 Flyway 升级路径应用 V20 及后续迁移。新增约束会再次检查现有数据，发现违反规则的记录就失败，不能跳过失败继续发布。

MySQL 的 DDL 不保证整个 SQL 迁移原子回滚。如果迁移中途失败，前面的约束可能已经建立。此时应先保留错误信息并检查 `flyway_schema_history` 和实际约束，处理数据原因后制定恢复步骤；不要未经核对直接执行 `flyway repair` 或重新运行全部语句。

## 回归验证

`SchemaGenerationBaselineTest` 验证全新 H2 数据库约束、异常历史库存和重复库存锁会阻止升级且不被自动改写。`SchemaGenerationBaselineMySqlTest` 在 MySQL 8.4 从旧版本升级，验证零价占位和未知成本保持原值，并验证新约束实际拒绝非法写入。两者共享同一组库存、金额、唯一性与流水边界断言。
