# Shop 物流轨迹数据同步与展示实施计划

## 目标

- 保留现有微信官方物流组件入口和本地承运商、运单号展示。
- 使用 `query_trace` / `query_follow_trace` 同步微信查询组件的当前物流状态。
- 对微信电子面单使用 `getPath` 同步详细轨迹节点。
- 小程序对所有快递发货订单固定展示物流轨迹区域；没有节点时展示明确空态。
- 管理后台可查看规范化后的轨迹状态、节点、同步时间和安全错误信息，并可手动刷新。
- 本阶段不根据物流状态修改 `shop_order.status`，不改变现有确认收货、自动收货、售后或退款状态机。

## 边界与安全约束

- 微信接口只允许后端调用；不向客户端暴露 access token、waybill token、OpenID、支付交易号或原始响应体。
- `query_trace` 与 `getPath` 独立执行并独立记录结果，一方失败不能覆盖另一方的成功数据。
- 轨迹节点只保存规范化字段；节点文本中的手机号在落库前脱敏。
- 小程序只能同步和读取本人订单；后台读取沿用 `order:read`，主动同步使用独立权限。
- 重复同步使用数据库 claim/CAS 防止并发上游调用；短时间重复打开页面返回缓存结果。
- 物流状态仅作为履约子状态保存和展示，绝不写入订单状态或订单状态日志。

## 数据模型

### `shipment_tracking_snapshot`

每个 `order_shipment` 一行，保存：

- `query_trace` 是否支持、同步状态、规范化物流状态、最近错误；
- `getPath` 是否支持、同步状态、最近错误；
- 最近尝试与成功时间；
- 同步 claim token 和 claim 时间。

### `shipment_tracking_event`

保存 `getPath` 返回的规范化节点：发生时间、动作类型、已脱敏描述和显示顺序。每次成功同步以同一事务替换该运单的节点集合。

## 后端实现

1. 新增微信轨迹 provider，分别调用：
   - `express/delivery/open_msg/query_trace` 或 `query_follow_trace`；
   - `express/business/path/get`。
2. 新增轨迹同步协调器和状态仓储：
   - 查询组件登记成功且存在 token 时同步摘要状态；
   - 存在微信电子面单完整标识时同步 `getPath`；
   - 支持部分成功、缓存、并发 claim 和安全错误信息。
3. 新增 owner-only 小程序同步接口和后台同步接口，响应统一轨迹 DTO 并设置 `no-store`。
4. 新增后台同步权限并分配给超级管理员和订单菜单。

## 客户端实现

### 小程序

- 订单基础详情先正常显示，再独立同步轨迹，避免微信接口阻塞整个订单页。
- 快递订单固定显示轨迹区域：加载、有节点、等待轨迹、来源不支持、同步失败五种状态。
- 保留“查看全部物流”官方组件入口；官方入口不可用时仍保留本地轨迹和运单信息。

### 管理后台

- 订单详情物流诊断区新增当前物流状态、两个数据源的支持/同步状态、同步时间和错误说明。
- 展示完整轨迹时间轴和空态。
- 提供“立即同步物流”按钮，完成后刷新当前订单轨迹，不修改订单状态。

## 验证

- Provider 精确请求体、成功/失败/超限/敏感日志测试。
- 状态仓储的 owner 隔离、部分成功、节点替换、缓存和并发 claim 测试。
- Controller 权限与 `Cache-Control: no-store` 测试。
- 证明同步签收状态后订单仍保持 `SHIPPED`，且不新增订单状态日志。
- 小程序固定轨迹区域、空态和官方组件入口测试。
- 后台类型检查、轨迹格式化测试和生产构建。
- 后端聚焦测试、完整测试、Mini Program `pnpm check`、`git diff --check`。
