# Shop 在线客服受控转接实施计划

日期：2026-07-15

## 行为目标

- 普通客服只能向“实时连接在线、已开始接待、未达到接待上限”的客服发起转接申请，不能直接修改会话负责人。
- 转接申请由目标客服在 60 秒内接受或拒绝；接受前会话仍由原客服负责，拒绝或超时不影响当前接待。
- 每个客服默认最多同时接待 5 个 `ACTIVE` 会话；达到上限后不能再被认领或接受普通转接。
- 客服可以在在线客服页面切换“开始接待/暂停接待”；实时连接断开时对外统一显示离线。
- 当前客服可以把会话退回 `WAITING` 公共队列，清空负责人，等待其他可接待客服认领。
- 超级管理员可以对在线但忙碌或满负荷的客服执行强制转接，并记录原因；离线客服始终不可接收实时会话。
- 只有明确拥有 `R_CUSTOMER_SERVICE` 角色的账号成为普通转接候选人；仅有 `R_SUPER` 的账号负责监管，不默认参与接待。

## 数据模型

1. `customer_service_agent_state`
   - `admin_user_id`：客服账号。
   - `work_status`：`AVAILABLE` 或 `BUSY`；是否在线由实时连接动态计算。
   - `max_active_conversations`：默认 5。
   - `updated_at`：状态更新时间。
2. `customer_service_transfer_request`
   - 会话、发起客服、目标客服、原因、状态、到期时间和处理时间。
   - `pending_key=1` 配合唯一索引保证一个会话最多一个待处理申请；处理后置空。

## 后端切片

1. 扩展实时连接中心，支持按后台用户判断在线状态和向指定后台用户推送事件。
2. 增加客服工作状态、候选人负载和本人状态接口。
3. 将原直接转接接口替换为创建转接申请；增加待处理列表、接受、拒绝和退回队列接口。
4. 接受转接时原子校验：申请仍待处理、未超时、会话仍由原客服负责、目标仍在线且可接待、容量仍可用。
5. 增加超级管理员强制转接接口：跳过忙碌和容量限制，但不跳过在线、账号及角色校验。
6. 认领会话时也校验本人在线、可接待和容量，避免绕过接待上限。
7. 转接真正完成后才写系统消息并通知用户；申请、拒绝和超时只通知后台客服。

## 后台切片

- 页面顶部增加本人接待状态与当前负载，提供“开始接待/暂停接待”。
- 转接候选人展示在线状态、接待状态和 `当前数量/上限`，不可接收者禁用。
- 转接时填写原因并发送申请，不再立即显示“已转接”。
- 目标客服收到实时确认弹窗，也可从页面中的待处理转接入口接受或拒绝。
- 当前负责人增加“退回待接待”操作。
- 超级管理员在有管理权限时可选择强制转接，并必须二次确认、填写原因。

## 明确边界

- 第一版按单个后端实例运行，在线状态使用当前进程中的 WebSocket 连接；未来多实例部署时再替换为 Redis TTL presence。
- 不自动把短暂断线客服名下的进行中会话重新分配，避免网络抖动导致会话跳转；管理员可手动退回或强制转接。
- 不新增独立客服管理页面；接待上限先写入数据模型并使用默认值 5，后续可在账号管理中开放配置。
